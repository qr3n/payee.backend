# Интеграция конкурентной генерации платежей (SSE Race)

## Общая концепция

Для ускорения выдачи реквизитов и получения резервных ссылок на оплату бэкенд запускает все доступные бот-сценарии параллельно в режиме конкуренции (гонки).
Каждый сценарий задействует отдельный свободный Telegram-аккаунт из пула.

Чтобы фронтенд не ждал завершения всех сценариев и мог сразу отобразить пользователю самую быструю ссылку (а остальные подгружать по мере готовности в качестве запасных способов), эндпоинт работает по протоколу **Server-Sent Events (SSE)**.

---

## Спецификация эндпоинта

- **URL:** `POST /api/v1/payments/race`
- **Заголовки:**
  - `Content-Type: application/json`
  - `Accept: text/event-stream`
- **Тело запроса:**
  - `client_user_id` (string, обязательное): уникальный ID пользователя (Telegram ID, внутренний ID юзера).
  - `amount` (decimal/string, обязательное): сумма платежа (например, `"250.00"`).
  - `currency` (string, по умолчанию `"RUB"`): валюта.
  - `timeout_sec` (float, опционально, по умолчанию `120.0`): максимальное время ожидания гонки.
  - `meta` (object, опционально): произвольные метаданные (номер заказа, корзина и т.д.).

> **Обратите внимание:** Стандартный браузерный объект `EventSource` умеет делать только `GET`-запросы. Так как для передачи параметров создания платежа используется `POST`, на фронтенде следует использовать `fetch` с чтением тела через `ReadableStream` либо специализированные решения вроде `@microsoft/fetch-event-source` или аналоги в axios/ky.

## Формат потока событий (SSE)

Сервер удерживает соединение открытым и передает стандартные SSE-пакеты вида:
```http
event: <имя_события>
data: <json_строка>

```

В рамках одного запроса приходят 4 типа событий:

### 1. `started`
Отправляется сразу после проверки свободных аккаунтов и их блокировки под сценарии.
- **Назначение:** сигнализирует, что гонка началась.
- **Полезная нагрузка (`data`):**
  - `batch_id`: уникальный UUID пачки платежей, объединяющий все создаваемые в этой гонке варианты.
  - `scenarios`: список сценариев, которые удалось запустить в параллель.

### 2. `payment`
Отправляется по мере того, как тот или иной бот успешно генерирует платежную ссылку. Приходит несколько раз (по одному на каждый успешный сценарий), отсортированно по скорости генерации (самый быстрый приходит первым).
- **Назначение:** передача готовых ссылок на оплату.
- **Полезная нагрузка (`data`):**
  - `batch_id`: UUID общей пачки платежей.
  - `payment_id`: уникальный UUID конкретного созданного платежа в базе данных.
  - `scenario_id`: идентификатор сценария (`starslly_bot`, `helperstars_bot`, `starshoppik_bot` и т.д.).
  - `payment_link`: итоговая ссылка на оплату.
  - `is_sbp_resolved`: булевый флаг (`true`/`false`). Если `true`, ссылка уже автоматически преобразована в прямую ссылку СБП Национальной системы платежных карт (`https://qr.nspk.ru/...`). Такую ссылку можно напрямую открывать на мобильном устройстве для вызова банковского приложения или генерировать из нее QR-код.
  - `generation_time_sec`: суммарное время (в секундах) от старта гонки до получения этой ссылки.
  - `stage_timings`: массив с разбивкой по времени каждого этапа (подключение, ввод данных в боте, парсинг СБП и т.д.).

### 3. `error`
Отправляется, если отдельный сценарий упал с ошибкой, либо если был достигнут общий таймаут `timeout_sec`.
- **Назначение:** логирование или отображение статуса конкретного провайдера.
- **Полезная нагрузка (`data`):**
  - `error`: код ошибки (`scenario_failed`, `timeout`, `no_accounts_available`).
  - `message`: человекочитаемое описание.

### 4. `done`
Всегда закрывающее событие потока. Отправляется после того, как все запущенные сценарии завершились (успехом или ошибкой) либо наступил таймаут. После этого события соединение завершается сервером.
- **Назначение:** флаг завершения загрузки всех вариантов (выключение лоадеров на UI).
- **Полезная нагрузка (`data`):**
  - `batch_id`: UUID пачки.
  - `total`: сколько сценариев участвовало.
  - `succeeded`: сколько завершилось успешно.
  - `failed`: сколько упало с ошибкой.
  - `duration_sec`: полное время работы гонки.

## Рекомендуемый пользовательский сценарий (UX)

1. Пользователь нажимает «Оплатить». Фронтенд отправляет `POST /api/v1/payments/race` и показывает лоадер.
2. При получении первого события `payment`:
   - Лоадер скрывается.
   - Пользователю сразу отображается кнопка оплаты или QR-код с полученной ссылкой (`payment_link`). Для пользователя ожидание минимально (обычно от 4 до 8 секунд).
3. При получении последующих событий `payment`:
   - Ссылки сохраняются в локальном стейте и отображаются как «Запасной способ оплаты» или альтернативный шлюз на случай, если по первой ссылке возникли проблемы в банке.
4. При получении события `done`:
   - Завершается фоновое ожидание запасных ссылок.
5. Автоматический реконнект (который обычно встроен в некоторые SSE-библиотеки) для этого эндпоинта **должен быть выключен**, чтобы при сетевых сбоях не инициировать повторные параллельные заказы без ведома пользователя.
