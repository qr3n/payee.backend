## 1. Критично: `GENERATING` и `RECONCILIATION_REQUIRED` не сохраняются при ошибке запроса

**Приоритет: P1, блокирует приёмку восстановления.**

**Где:** [регистрация операции](https://github.com/qr3n/payee.backend/blob/cfeb2d37ffb77260992bb10237a080441fc388ea/services/api/app/modules/payments/service.py#L300-L338), [обработка ошибки](https://github.com/qr3n/payee.backend/blob/cfeb2d37ffb77260992bb10237a080441fc388ea/services/api/app/modules/payments/service.py#L497-L573), [DB dependency](https://github.com/qr3n/payee.backend/blob/cfeb2d37ffb77260992bb10237a080441fc388ea/services/api/app/api/deps.py#L42-L56).

Агент добавил:

```python
async with session.begin_nested():
    session.add(payment)
    await session.flush()
```

**Это savepoint, а не отдельный commit.**

Регистрация остаётся внутри общей транзакции HTTP-запроса. При исключении `get_db()` выполняет `rollback()`, поэтому исчезают:

- предварительная запись `GENERATING`;
- выставленный в обработчике ошибки `FAILED`;
- выставленный `RECONCILIATION_REQUIRED`.

### Что это означает

1. Внешний счёт создан.
2. Следующий этап завершается ошибкой.
3. Код выставляет `RECONCILIATION_REQUIRED` и делает `flush`.
4. Исключение передаётся наружу.
5. Dependency откатывает всю транзакцию.
6. В БД нет ни счёта, ни записи для сверки.

При аварийном завершении процесса предварительная запись тоже не сохранится.

Уникальный constraint теперь помогает конкурирующим запросам **в нормальном успешном выполнении**, но не решает этот сценарий.

### Что доработать

Нужны отдельные, короткие и фиксируемые транзакции:

1. **Регистрация:** создать операцию `GENERATING`, сохранить hash, сделать commit **до внешнего действия**.
2. **Назначение ресурсов:** сохранить аккаунт, владельцев резерваций и этап попытки.
3. **Внешний вызов:** вне длительной DB-транзакции.
4. **Завершение:** в новой транзакции сохранить результат и `PENDING`.
5. **Неизвестный результат:** в новой транзакции сохранить `RECONCILIATION_REQUIRED`, затем вернуть ошибку пользователю.

Не использовать повреждённую после DB-ошибки session для «попытки сохранить статус» через `suppress(Exception)`.

**Важно:** `result is None` не доказывает отсутствие внешнего счёта. Запрос мог выполниться у провайдера, а ожидание ответа — завершиться таймаутом.

### Приёмочный тест

Искусственно оборвать выполнение после внешнего создания. После закрытия исходной session **новая независимая session** должна увидеть сохранённую попытку для сверки. Повтор с тем же ключом не вызывает провайдера ещё раз.

## 2. Потеря lease только выставляет флаг — диалог продолжает работать

**Приоритет: P1.**

**Где:** [`AccountLeaseRenewer`](https://github.com/qr3n/payee.backend/blob/cfeb2d37ffb77260992bb10237a080441fc388ea/services/api/app/modules/payments/scenarios/state.py#L252-L308).

Продление теперь действительно подключено. Но при отказе:

```python
self._lost_event.set()
break
```

Основной сценарий не ждёт этот event и не проверяет `is_lost`. Он продолжает отправлять команды в Telegram и может успешно вернуть ссылку, уже не владея аккаунтом.

Проверки владения при входе в context manager тоже нет: первый renewal происходит только через 30 секунд.

### Что доработать

Нужен исполнитель, который связывает lease и выполняемую операцию:

- проверяет владение перед стартом;
- продлевает lease;
- при потере владения отменяет операцию;
- дожидается завершения её cleanup;
- не выдаёт успешный результат после потери lease;
- сохраняет неизвестный внешний результат для сверки.

Лучше передавать coroutine-фабрику в такой исполнитель и отдельно ожидать **операцию либо потерю lease**. Просто проверить `is_lost` после завершения недостаточно: команды уже могли перемешаться с другим исполнителем.

Для warmup renewal должен охватывать также получение/подключение клиента, если оно способно занять значимое время.

### Приёмочный тест

Во время заблокированного fake-диалога заменить lock на другого владельца. Проверить, что первый диалог остановился и больше не отправляет команды. Сейчас этого не происходит.

## 3. Идемпотентность гонки добавлена небезопасным `GET → SET`

**Приоритет: P1.**

**Где:** [`start_payment_race`, строки 1313–1337](https://github.com/qr3n/payee.backend/blob/cfeb2d37ffb77260992bb10237a080441fc388ea/services/api/app/modules/payments/service.py#L1313-L1337).

Сейчас:

```python
existing_batch = await redis.get(race_idem_key)
...
await redis.set(race_idem_key, str(batch_id), ex=1800)
```

### Оставшиеся ошибки

- Два запроса могут одновременно прочитать отсутствие ключа и запустить **две гонки**.
- Payload не сравнивается: другой amount/recipient/scenario list с тем же ключом возвращает прежний batch.
- Ключ записывается **до проверки доступных аккаунтов и создания batch-buffer**.
- Если первый запрос не смог стартовать, повтор получает ID **несуществующей гонки**.
- При повторе всегда возвращается `running`, даже если гонка завершилась.
- Список сценариев повторного ответа берётся из нового запроса либо жёстко заданного списка, а не исходного batch.
- Idempotency key живёт 30 минут, SSE-buffer — пять: можно получить batch, результаты которого уже недоступны.

### Что доработать

Использовать сохраняемый batch с уникальным ключом и request hash — по той же схеме, что и обычную операцию:

- атомарная регистрация;
- фактические выбранные сценарии;
- статус;
- результат запуска;
- восстановление после сбоя.

**Не ограничиваться добавлением `nx=True`:** это исправит только одну из перечисленных проблем.

## 4. Request hash по-прежнему не учитывает фактического получателя

**Приоритет: P1.**

**Где:** [hash](https://github.com/qr3n/payee.backend/blob/cfeb2d37ffb77260992bb10237a080441fc388ea/services/api/app/modules/payments/service.py#L61-L91), [параметры HelperStars](https://github.com/qr3n/payee.backend/blob/cfeb2d37ffb77260992bb10237a080441fc388ea/services/api/app/modules/payments/scenarios/helperstars_scenario.py#L63-L71).

В hash включён ключ:

```python
"recipient"
```

Сценарии используют:

```python
"recipient_username"
```

Поэтому одинаковый idempotency key с получателем A и затем B может вернуть старый счёт вместо конфликта.

Также начальное сохранение:

```python
meta={"request_hash": payload_hash, **payment_in.meta}
```

позволяет входному `meta` переписать внутренний `request_hash`.

### Что исправить

Минимальная локальная правка:

```python
# В списке значимых полей:
"recipient_username"

# При сохранении:
meta={**payment_in.meta, "request_hash": payload_hash}
```

Но правильнее вычислять hash из **нормализованной спецификации заказа**:

- фактический recipient;
- фактические bot/channel;
- применённый rate;
- amount/currency;
- для гонки — сценарии и значимые параметры выполнения.

Внутренний hash лучше хранить отдельным полем, а не в произвольном `meta`. Callback тоже не должен его изменять.

## 5. Owner-проверка idempotency lock сравнивает токен с целым JSON

**Приоритет: P1/P2.**

**Где:** [запись Redis](https://github.com/qr3n/payee.backend/blob/cfeb2d37ffb77260992bb10237a080441fc388ea/services/api/app/modules/payments/service.py#L247-L258), [освобождение](https://github.com/qr3n/payee.backend/blob/cfeb2d37ffb77260992bb10237a080441fc388ea/services/api/app/modules/payments/service.py#L552-L573).

Значение idempotency key — JSON с полем `owner`. А `_eval_release_lock()` использует Lua, сравнивающий **всё значение Redis** с переданным токеном.

Они никогда не равны. Обычное освобождение этого ключа не работает.

Отдельно запись `completed`/`reconciliation_required` всё ещё выполняется без проверки владельца и до надёжной фиксации результата.

### Что исправить

Разделить:

- lease-key со строковым owner token;
- состояние операции в БД;
- необязательный кэш результата.

Тогда существующий compare-and-delete подходит lease-key. Не применять его к JSON-состоянию.

Сбой необязательного Redis-кэша после успешного DB-commit не должен превращать созданный платёж в ошибку с откатом.

## 6. Предрегистрация уведомления оставляет session в failed-state при конфликте

**Приоритет: P1.**

**Где:** [`notifications.py`, строки 203–228](https://github.com/qr3n/payee.backend/blob/cfeb2d37ffb77260992bb10237a080441fc388ea/services/api/app/modules/payments/notifications.py#L203-L228).

Агент перенёс вставку события до изменения платежа — это правильно. Но сделал:

```python
try:
    await session.flush()
except Exception:
    ...
    return None
```

После `IntegrityError` session требует rollback. Возврат `None` не восстанавливает транзакцию. Последующий commit или обработка следующего события упадут.

Кроме того, любая DB-ошибка ошибочно объявляется «событие уже зарегистрировано».

### Что доработать

- Для новой записи: PostgreSQL `INSERT ... ON CONFLICT DO NOTHING` либо savepoint с обработкой **только ожидаемого уникального конфликта**.
- Для существующего `unmatched`: `FOR UPDATE`, `populate_existing`, повторная проверка статуса после получения блокировки.
- Не подавлять остальные DB-ошибки.
- Финансовые побочные действия — после DB-фиксации через outbox.

При варианте savepoint `session.add(active_event)` должно находиться **внутри** `begin_nested()`, иначе создание savepoint может предварительно flush уже добавленного объекта.

Отдельная обработка сохранённых unmatched-событий из БД всё ещё нужна: повторное чтение последних пяти сообщений не гарантирует, что событие будет найдено снова.

## 7. Новые статусы не встроены в явную модель переходов

**Приоритет: P1.**

**Где:** [`mark_payment_status`](https://github.com/qr3n/payee.backend/blob/cfeb2d37ffb77260992bb10237a080441fc388ea/services/api/app/modules/payments/service.py#L640-L687), [`cancel_payment`](https://github.com/qr3n/payee.backend/blob/cfeb2d37ffb77260992bb10237a080441fc388ea/services/api/app/modules/payments/service.py#L736-L765).

В enum появились `GENERATING` и `RECONCILIATION_REQUIRED`, но lifecycle по-прежнему проверяет только прежние terminal states.

В частности, `PENDING` можно через generic callback перевести обратно в `GENERATING`. Комментарий «Valid transition from PENDING» это не ограничивает.

### Что исправить

Обычную callback-операцию ограничить явными переходами:

```python
ALLOWED_CALLBACK_TRANSITIONS = {
    PaymentStatus.PENDING: {
        PaymentStatus.PAID,
        PaymentStatus.CANCELLED,
        PaymentStatus.EXPIRED,
        PaymentStatus.FAILED,
    },
}
```

После проверки идемпотентного повтора:

```python
allowed = ALLOWED_CALLBACK_TRANSITIONS.get(locked_payment.status, set())
if callback.status not in allowed:
    raise AppException(
        message="Invalid payment status transition.",
        code="INVALID_PAYMENT_TRANSITION",
        status_code=409,
    )
```

Завершение генерации и ручная сверка должны иметь **отдельные операции**, свои права и аудит. Этот фрагмент не заменяет их.

## 8. В race-path есть ошибка `result` до присваивания

**Приоритет: P2, конкретный дефект.**

**Где:** [`_run_race_scenario_task`](https://github.com/qr3n/payee.backend/blob/cfeb2d37ffb77260992bb10237a080441fc388ea/services/api/app/modules/payments/service.py#L1151-L1260).

`result = None` находится внутри `try`, **после** проверки сценария и pending-slot.

Если эта проверка выбросит исключение, обработчик выполняет:

```python
if result is not None:
```

и получает `UnboundLocalError`, маскируя исходную причину.

### Исправление

Перенести:

```python
result = None
```

к остальным начальным переменным **до `try`**.

Также cancellation внутри HelperStars/Starslly по-прежнему не проходит через их `except Exception`. Токен резервации нужно передавать менеджеру попытки сразу после захвата, а не только вместе с успешным результатом.

## Что ещё не закрыто из исходного ревью

Без повторения всего отчёта, остаются:

- outbox и согласование DB-переходов с Redis-освобождением;
- сохраняемый batch и восстановление после аварийного завершения API;
- сверка фактической суммы/валюты внешнего счёта;
- единый владелец Telegram-аккаунта;
- PostgreSQL CI через миграции — текущие тесты по умолчанию используют SQLite и `create_all`;
- безопасный backend-flow авторизации по телефону;
- отдельный SSE-пул и retention активных гонок.

**Starslly теперь безопаснее, но автоматическая оплата фактически отключена:** текущий parser не извлекает order ID, а тест успешного точного сопоставления подменяет parser. Это допустимое временное ограничение, но его нужно явно описать пользователям и предоставить процесс ручной сверки.

## Следующая приёмка: конкретные критерии

Чтобы не продолжать цикл «добавили функцию — забыли гарантию», агенту нужно проверить следующие сценарии:

1. После ошибки или остановки запроса попытка **остаётся в БД**.
2. Повтор такой попытки **не создаёт второй внешний счёт**.
3. Потеря lease **останавливает внешние действия**.
4. Два одинаковых race-запроса создают **один реальный batch**.
5. Изменение `recipient_username` с прежним ключом даёт `409`.
6. Конфликт вставки notification не ломает session и не откатывает ранее корректно обработанные события.
7. Callback не возвращает платёж из `PENDING` в `GENERATING`.
8. Ошибка pending-slot сохраняет исходную причину, а не `UnboundLocalError`.

**Итог:** зелёный CI и несколько существенных исправлений подтверждаю. Но полную готовность пока нет: savepoint не обеспечивает сохранность операции после сбоя, а флаг потери lease не обеспечивает прекращение работы. Это два главных блокера следующего прохода.
